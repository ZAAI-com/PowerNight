# PowerNight 2.0.1 release notes

Patch release on top of [2.0.0](2.0.0.md). No database migration, no config
changes, no API changes. Upgrade and rollback steps are the same as 2.0.0.

## Fixes

- **Crash loop on bind-mounted data folders (Synology).** 2.0.0 restricts `/data`
  and the Tesla token files to owner-only permissions on startup. Only the owner
  may change permissions, so when `/data` belongs to a host user (for example a
  Synology share granted to the container via DSM ACLs) startup failed with
  `Failed to start web interface: [Errno 1] Operation not permitted` and the
  container restarted repeatedly. PowerNight now logs a
  `Cannot restrict permissions` warning naming both uids and keeps running.
  Paths owned by the container user still fail closed if they cannot be secured.
- The "Failed to start web interface" log entry now includes the full traceback.

## Recommended after upgrading

To keep Tesla tokens private and silence the warning, make the container user
own the data folder (see the Synology notes in the [README](../README.md#synology-nas)):

```bash
docker run --rm --entrypoint id zaaicom/powernight:2.0.1   # shows the container uid/gid
sudo chown -R <uid>:<gid> /volume1/docker/PowerNight-Data
```

## Publication

Follow the 2.0.0 [versioned publication](2.0.0.md#versioned-publication-after-merge-not-performed-by-local-validation)
steps with `2.0.1`: validate with `python scripts/check_release_version.py 2.0.1`,
tag the merged `main` commit as `2.0.1`, and run Docker Promote only after a canary.
