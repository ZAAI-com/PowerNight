# PowerNight 2.0.0 release notes and rollout

Status: release preparation; no release tag or image publication yet. Local
validation does not count as a live Powerwall canary. Keep `latest` unchanged.

## Changes

- React-only web UI with task presets, execution history, and toast feedback.
  Dashboard refreshes every 20 seconds while visible, without an interval dropdown.
- Tesla setup and reconnect use the shared connector and reload the selected
  account/site. Cached connection status remains available during slow requests;
  reconnects wait for in-flight Powerwall commands.
- Environment overrides remain runtime-only when saving settings; environment
  API keys and derived authentication flags no longer leak into saved config or
  newly created backups. Override values are omitted from diagnostic logs.
- Status reads avoid nested circuit-breaker locking. Read fallbacks retain their
  original cache age instead of making stale outage data appear fresh.
- Credential-bearing files are published atomically with private permissions;
  unsafe token directories fail closed rather than silently weakening access.
- Duplicate preset names return HTTP 409 without database SQL in the response;
  malformed parameters return 422 and built-in deletion returns 403.
- TypeScript checks actually include source and tests. Frontend and backend CI
  enforce the supported checks; Docker uses Python 3.14 and frontend CI Node 26.
- Versioned Docker images are staged first. A separate digest-verified promotion
  workflow updates `latest` only after an explicitly verified live canary.

## Compatibility and data migration

- Tesla cloud is the supported connection mode. Removed legacy profile,
  scheduling, demo, and enterprise surfaces are not compatibility promises.
  Review integrations against the retained `/api/v1` and `/api/auth` routes.
- Authentication is optional on a trusted LAN. A nonempty API key or complete
  Basic-auth credential pair enables protection. Explicit authentication without
  usable credentials fails closed. Never expose the service directly to the
  public internet.
- Startup adds task execution columns, removes the old `schedule_entries` table,
  deduplicates preset names (retaining the oldest row), and seeds built-in presets.
  Legacy schedule entries are not converted to Planner tasks: inventory them
  before upgrading and recreate needed schedules explicitly.
- Already-persisted environment secrets and backup contents are not automatically
  scrubbed. If an earlier affected build saved a key, remove that file-owned copy
  and rotate it before distributing the configuration or backups.
- YAML settings are separate from the database. Use the tested release override
  below; the base Compose file alone still uses `latest` and image-local YAML.
- Existing backup files get owner-only permissions when listed or backed up;
  their contents are not scrubbed. Remove/rotate any previously persisted secrets.

## Persistent release configuration

Use these steps only on an explicitly selected installation after publication.
Do not execute them against production during local validation.

1. Keep `docker-compose.yml`, `compose.release.yml`, `.env.example`, and
   `config.example.yaml` together. Release assets are prepared with
   `python scripts/package_release.py`; verify `sha256sum -c SHA256SUMS` (macOS:
   `shasum -a 256 -c SHA256SUMS`). Until publication, use repository files.
2. **Fresh install only** (never overwrite an existing YAML):

   ```bash
   mkdir -p PowerNight-Data
   test ! -e PowerNight-Data/config.yaml
   cp -n config.example.yaml PowerNight-Data/config.yaml
   test -f .env || cp .env.example .env
   ```

   Set `TESLA_EMAIL` and optional `POWERNIGHT_API_KEY` in `.env`.
   `AUTOMATION_ENABLED=false` keeps an installation idle during setup; enable it
   explicitly only after checking tasks/site/timezone.
3. **Upgrade only:** stop the old service and back up its data, `.env`, deployment
   files, and effective YAML before recreation. If YAML is image-local, copy it
   from the stopped container before removing it:

   ```bash
   docker compose stop
   # Confirm the old effective config path first; this is the image default.
   test ! -e PowerNight-Data/config.yaml
   docker compose cp PowerNight:/app/config/config.yaml PowerNight-Data/config.yaml
   ```

   If persistent YAML already exists, preserve it; do not run either copy command.
   Never replace an upgrade config with the example. Keep the old image digest
   and a credential-protected backup for rollback.
4. Pull the versioned image and grant its runtime user access to the data directory
   and YAML (the latter must be writable for UI timezone saves):

   ```bash
   docker compose -f docker-compose.yml -f compose.release.yml pull
   docker compose -f docker-compose.yml -f compose.release.yml run --rm --no-deps --user root PowerNight python -c 'import os,pwd; from pathlib import Path; u=pwd.getpwnam("powernight"); paths=[Path("/data"),Path("/data/config.yaml")]; [(os.chown(p,u.pw_uid,u.pw_gid),os.chmod(p,0o700 if p.is_dir() else 0o600)) for p in paths]'
   docker compose -f docker-compose.yml -f compose.release.yml run --rm --no-deps PowerNight python -c 'import os; assert os.access("/data",os.W_OK); assert os.access("/data/config.yaml",os.W_OK)'
   docker compose -f docker-compose.yml -f compose.release.yml up -d
   ```

   Preserve ownership of existing database/token files too; do not recreate or
   delete them. On NAS/ACL mounts, verify runtime access and owner-only permissions
   before starting. Do not weaken permissions to bypass an error.
5. Check Settings timezone, tasks, presets, and auth; recreate with the same two
   Compose files and check that the settings persist.

## Validation gates

1. Validate the intended version with `python scripts/check_release_version.py 2.0.0`.
2. Require CI and Docker Health Test to pass for the exact release commit.
   Backend mypy is currently informational; record outstanding errors rather than
   treating that job as a release-blocking guarantee.
3. Run `./build.sh --no-docker`, build the image, then run
   `python scripts/release_smoke.py --image powernight-release:test`.
   The script uses disposable Compose projects/volumes and synthetic legacy data,
   tests protected and open API access, migrations, preset conflicts, config
   saving, and persistence through container recreation. It never sends device
   commands and is not a substitute for a real Tesla login/overnight canary.
4. Confirm `linux/amd64`, `linux/arm64`, and `linux/arm/v7` builds and manifests
   before declaring all three platforms supported for this release.

## Versioned publication (after merge; not performed by local validation)

1. Merge PR #2 only after all valid review feedback is addressed and CI passes
   on the final PR head. A live canary is **not** a merge gate for this release.
   Validate the merged `main` commit; all source versions must equal `2.0.0`.
2. Create an annotated numeric `2.0.0` tag at that commit and push it. A manual
   Docker Publish run must select `refs/tags/2.0.0`, not a branch.
3. Docker Publish builds version-only tags in GHCR and Docker Hub. Record the
   commit, run URL, and multi-arch digest; verify both registries and all platforms.
   **Docker `latest` stays unchanged.**
4. Package deployment assets with `python scripts/package_release.py` from that
   exact tagged checkout. Create the GitHub release with these assets, checksums,
   changes, compatibility notes, digest, and build-validation scope. Use
   `gh release create 2.0.0 --verify-tag --latest=false` with the prepared notes
   and explicit asset paths. **Do not designate it GitHub Latest.**

## Optional future live canary and promotion (separate authorization)

Local validation is the agreed scope. No canary installation has been selected.
A future canary must back up data/config, use the two-file pinned Compose setup
above, and verify real Tesla reconnect, the selected site, restarts, tokens,
correct timezone, and one full overnight scheduling cycle.

Only after that live gate and explicit promotion authorization, run Docker Promote
from `main` with the exact published digest/version and `canary_verified=true`.
The workflow verifies both registries and all platforms and promotes without
rebuilding. Registry writes are not atomic: inspect both tags after a failure.
Until then leave Docker `latest`, GitHub Latest, and production unchanged.

## Rollback

Stop the canary on missing tasks/tokens, incorrect site/reserve changes, repeated
command failures, duplicate executions, or crash loops. Restore the pre-upgrade
data/config backup and previous pinned image together while the service is
stopped, then start with Docker Compose. Do not assume an older binary can read
the migrated database. Reconcile any tasks created since the backup before
resuming automation. Never delete or replace production data during local tests.
