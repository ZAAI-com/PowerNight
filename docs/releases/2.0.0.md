# PowerNight 2.0.0 release notes and rollout

Status: release preparation; no release tag or image publication yet. Local
validation does not count as a live Powerwall canary. Keep `latest` unchanged.

## Changes

- React-only web UI with task presets, execution history, and toast feedback.
- Tesla setup and reconnect use the shared connector and reload the selected
  account/site. Cached connection status remains available during slow requests;
  reconnects wait for in-flight Powerwall commands.
- Environment overrides remain runtime-only when saving settings; environment
  API keys and derived authentication flags no longer leak into saved config or
  newly created backups. Override values are omitted from diagnostic logs.
- Duplicate preset names return HTTP 409 without database SQL in the response.
- TypeScript checks actually include source and tests. Frontend and backend CI
  enforce the supported checks; Docker uses Python 3.14 and frontend CI Node 26.
- Versioned Docker images are staged first. A separate digest-verified promotion
  workflow updates `latest` only after an explicitly verified live canary.

## Compatibility and data migration

- Tesla cloud is the supported connection mode. Removed legacy profile,
  scheduling, demo, and enterprise surfaces are not compatibility promises.
  Review integrations against the retained `/api/v1` and `/api/auth` routes.
- Authentication is optional on a trusted LAN. A nonempty API key or complete
  Basic-auth credential pair enables protection. Explicit authentication without
  usable credentials fails closed. Never expose the service directly to the
  public internet.
- Startup adds task execution columns, removes the old `schedule_entries` table,
  deduplicates preset names (retaining the oldest row), and seeds built-in presets.
  Legacy schedule entries are not converted to Planner tasks: inventory them
  before upgrading and recreate needed schedules explicitly.
- Already-persisted environment secrets and existing backups are not silently
  modified. If an earlier affected build saved a key, remove that file-owned copy
  and rotate it before distributing the configuration or backups.
- YAML settings are separate from the `/data` database. The image defaults to
  `/app/config/config.yaml`, which the supplied Compose file does not persist.
  Before recreating an existing container, preserve its effective configuration
  and arrange a writable config mount or set `POWERNIGHT_CONFIG_PATH` to an
  existing writable file under `/data`. Verify the timezone after recreation;
  mounting `/data` alone does not preserve changes to the image's YAML file.

## Validation gates

1. Validate the intended version with `python scripts/check_release_version.py 2.0.0`.
2. Require CI and Docker Health Test to pass for the exact release commit.
   Backend mypy is currently informational; record outstanding errors rather than
   treating that job as a release-blocking guarantee.
3. Run `./build.sh --no-docker`, build the image, then run
   `python scripts/release_smoke.py --image powernight-release:test`.
   The script uses disposable Compose projects/volumes and synthetic legacy data,
   tests protected and open API access, migrations, preset conflicts, config
   saving, and persistence through container recreation. It never sends device
   commands and is not a substitute for a real Tesla login/overnight canary.
4. Confirm `linux/amd64`, `linux/arm64`, and `linux/arm/v7` builds and manifests
   before declaring all three platforms supported for this release.

## Publication and canary (not authorized during local-only validation)

1. Merge PR #2 after the current checks pass. Validate the merged `main` commit.
   The Python, frontend, lockfile, and runtime versions must all equal `2.0.0`.
2. Create an annotated `2.0.0` tag at that merged commit and push that tag. Do not
   use `v2.0.0`: the publish workflow requires a stable numeric tag. For a manual
   publish, select the same release tag, not a branch.
3. Docker Publish builds version-only tags in `ghcr.io/zaai-com/powernight` and
   `zaaicom/powernight`. Record the commit, run URL, and returned multi-arch digest.
   Both registries must contain that digest; `latest` remains unchanged.
4. On an explicitly selected canary host, stop PowerNight and back up the entire
   `PowerNight-Data` directory, `.env`, and deployment/config files. Keep the
   previous image reference/digest. Treat the backup as credential-bearing data.
5. Pin the canary Compose service to the new version/digest and preserve its
   existing `/data` mount. Use `docker compose up -d`, never an unmounted container.
   Verify tasks, presets, logs, token persistence after recreation, correct site,
   timezone, real Tesla reconnect, and one complete overnight scheduling cycle.
6. Run Docker Promote from `main` only after that canary passes. Supply the exact
   publication digest and set `canary_verified=true`. It verifies both versioned
   tags and all platforms before promoting the same digest without rebuilding.
   Registry writes are not atomic: if one fails, inspect both `latest` tags and
   rerun with the same verified version/digest to finish the other registry.
7. Publish the GitHub release using the Changes and Compatibility sections above,
   plus image digests and validated platforms. Monitor one further scheduled cycle.

## Rollback

Stop the canary on missing tasks/tokens, incorrect site/reserve changes, repeated
command failures, duplicate executions, or crash loops. Restore the pre-upgrade
data/config backup and previous pinned image together while the service is
stopped, then start with Docker Compose. Do not assume an older binary can read
the migrated database. Reconcile any tasks created since the backup before
resuming automation. Never delete or replace production data during local tests.
